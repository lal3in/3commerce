# Wiki diagram sources (Archify)

The interactive wiki diagrams are generated by the **Archify** skill from the typed
JSON specs in this folder. Committing the source spec means the next update edits the
spec and re-delivers — no re-authoring from scratch.

| Spec | Type | Rendered page |
|------|------|---------------|
| `runtime-architecture.architecture.json` | architecture | `../runtime-architecture.html` |
| `readcopy-dataflow.dataflow.json` | dataflow | `../readcopy-dataflow.html` |

> The other diagram pages (`order-workflow`, `checkout-sequence`, `order-lifecycle`)
> predate this folder and have no committed spec yet — back-fill them the same way when
> they next need an update.

## Update a diagram

Point at the Archify skill package (`ARCHIFY` below is
`~/.claude/skills/archify` in this environment):

```bash
ARCHIFY=~/.claude/skills/archify

# 1. Edit the spec, then validate (must report 0 diagnostics at showcase quality)
node "$ARCHIFY/bin/archify.mjs" validate architecture \
  docs/help/diagrams/runtime-architecture.architecture.json --quality showcase --json

# 2. Deliver — renders, runs the artifact checks, and atomically writes the HTML
node "$ARCHIFY/bin/archify.mjs" deliver architecture \
  docs/help/diagrams/runtime-architecture.architecture.json \
  docs/help/runtime-architecture.html --quality showcase --json
```

Use `dataflow` (not `architecture`) for `readcopy-dataflow.dataflow.json`. `deliver`
exits non-zero on any check failure and leaves the previous HTML untouched.

## Conventions

- `meta.quality_profile` must be `"showcase"`; every delivery must validate with **0**
  diagnostics.
- Keep ≤ ~12 primary nodes and one clear main path; prefer automatic routing over
  `via`/`labelAt` unless a diagnostic calls for it.
- Facts only — these maps mirror the code (services, events, boundaries). Update the
  spec when the architecture changes, not just the prose pages.
