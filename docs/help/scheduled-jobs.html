Scheduled jobs

Recurring background work — posting the daily ledger journal, renewing subscriptions, closing usage periods, going live with scheduled content — runs as cron-triggered scheduled jobs. Each job lives in the service that owns its data; the Admin Mission Control page is the single manager where you see every job, run one on demand, pause/resume it, or change its schedule.

Where: Admin → Mission Control → Scheduled jobs (src/Admin/Components/Pages/MissionControl.razor). The admin role is required. Mission Control reads each owning service's live schedule directly and enriches it with run history aggregated by the Workflow service.

The jobs that exist today

Four jobs ship with the platform. Each is registered in its owning service's Program.cs via AddScheduledJobs(…) and implements IScheduledJob.

ServiceJobSchedule (cron)What it does
marketingscheduled-publish0 * * * * ? — every minute Applies due content publishes: anything whose scheduled go-live time has arrived is published. Publish latency ≤ 60s. No-op when nothing is due. ScheduledPublishJob.
paymentssubscription-auto-renew0 0/15 * * * ? — every 15 min Sweeps due subscription renewals and charges them off-session against the saved payment method; each storefront renews at most once per day once its configured window has passed, and a failed charge marks the subscription past-due (dunning). Idempotent. SubscriptionAutoRenewJob.
paymentsdaily-journal0 0 2 * * ? — 02:00 UTC daily Posts the prior UTC day's ledger journal to Xero (the scheduled half of the daily-journal job). Idempotent per date, so a re-run for the same day is safe. DailyJournalScheduledJob.
usageusage-period-close0 0 * * * ? — hourly Closes metered usage periods that have ended: bills any unbilled overage and rolls each due balance to its next period. Idempotent — a re-run before new usage is a no-op. UsagePeriodCloseScheduledJob.

The central workflow service registers the scheduler too but owns no jobs of its own — it is the aggregator that collects every service's run history (JobRunRecorded events) so Mission Control can show one unified list.

How a job runs

  1. Trigger. Quartz fires the job's cron trigger (or you press Run now). A persistent, clustered Quartz store can be enabled so schedules survive restarts and only one node fires in a cluster (Scheduling options); otherwise an in-process scheduler is used.
  2. Execute. The job resolves in a fresh per-fire DI scope (so it can use a scoped DbContext) and JobExecutor runs its ExecuteAsync. Transient failures are retried up to a bounded count before the run is recorded failed.
  3. Record. Every fire is written to the owning service's local JobRuns table (Running → Succeeded/Failed, with duration and any error), and a JobRunRecorded event is published so the Workflow service projects it into the shared run history.
  4. Surface. Mission Control reads each service's live schedule (Next fire, paused state) and the Workflow run history (Last run status + duration) and renders them together.
Idempotency. Every job is safe to run more than once — Run now and retries never double-charge or double-post. That is why running a job on demand is a safe operator action.

Using the jobs from Mission Control

The Scheduled jobs table shows one row per job: Service, Job, Schedule (cron), Next fire, Last run, State, and per-row actions.

  • Run now — triggers the job immediately, regardless of its cron (and even if paused). Because jobs are idempotent this is safe. The row's Last run updates to the new run's outcome once it completes and records.
  • Pause / Resume — Pause stops the cron from firing the job without removing it; Resume re-enables it. A paused job can still be run with Run now. The paused state is persisted (a schedule override), so it survives restarts.
  • Edit — change the cron expression inline and Save. The new schedule is persisted as an override and applied immediately; an invalid cron is rejected with the reason shown. Use standard 6-field Quartz cron (sec min hour day month day-of-week) — e.g. 0 0 2 * * ? is 02:00 daily.

Adding a job

A new scheduled job is code, added to the service that owns the data it touches:

  1. Implement IScheduledJob (src/BuildingBlocks/Infrastructure/Scheduling/ScheduledJob.cs): a Name, a default CronSchedule, and ExecuteAsync that does the work. Keep it idempotent. Inject the service's scoped services (e.g. its DbContext, a domain service) via the constructor.
  2. Register it in the service's Program.cs:
    builder.Services.AddScheduledJobs(builder.Configuration, "usage", jobs => jobs.Add<MyJob>("my-job", "0 0 * * * ?"));
    The first argument is the owning-service key (stamped on run/descriptor events so the manager can route control back here).
  3. Persist run history — the service's DbContext must call modelBuilder.ConfigureJobRuns() (and ConfigureScheduleOverrides()) so the local JobRuns/ScheduleOverrides tables exist, register EfJobRunStore<MyDbContext>, and expose the control endpoints with app.MapJobControl(). The service must also be added to MissionControl.razor's JobServices list so the manager reads its schedule.
Outbox gotcha: the run-history event is published through the EF outbox, which only sends on the store's SaveChanges. JobExecutor publishes JobRunRecorded before its final save so the message actually flushes — a job whose run never appears in Mission Control is usually a broken publish-then-save order or a missing ConfigureJobRuns.

Removing or disabling a job

  • Stop it temporarily — Pause it in Mission Control. It stays listed but never fires until resumed. No deploy needed.
  • Remove it permanently — delete its .Add<MyJob>("my-job", …) registration from the owning service's Program.cs (and the job class) and redeploy. The historical JobRuns rows remain for the audit trail; the job simply no longer appears or fires.

API surface

Mission Control drives everything through the gateway, which forwards /api/{service}/admin/jobs/* to the owning service. The admin role is required.

PurposeCall
List live scheduleGET /api/{service}/admin/jobs
Run nowPOST /api/{service}/admin/jobs/{name}/run
Pause / ResumePOST /api/{service}/admin/jobs/{name}/pause · …/resume
Reschedule (cron)PUT /api/{service}/admin/jobs/{name}/schedule with { cron }
Aggregated run historyGET /api/workflow/admin/workflow/runs
